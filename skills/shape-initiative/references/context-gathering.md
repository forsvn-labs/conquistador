# Gather decision context

Read the request and available project instructions before asking questions. Inspect relevant product documents, implementation constraints, prior decisions, and authorized evidence. Do not assume a particular workspace layout exists on a standalone host.

Record what is already known, its source, and the material gap that could change the recommendation. Ask at most one bundled question for that gap. A clear implementation request does not need an interview.

For an unresolved decision, use [define the decision](decision-checks/decision-record.md). Add [demand evidence](decision-checks/demand-evidence.md) when adoption is uncertain, and [commitment planning](decision-checks/commitment-plan.md) when the next step creates obligations.

Load only the applicable checks:

| Decision concerns | Check |
|---|---|
| Consumer activation, return use, or acquisition | [Consumer adoption](decision-checks/consumer-adoption.md) |
| Inventory, fulfillment, or returns | [Physical product economics](decision-checks/physical-product-economics.md) |
| A buyer and workflow inside an organization | [Business workflow](decision-checks/business-workflow.md) |
| A lesson from an earlier attempt | [Prior attempts](decision-checks/prior-attempt-review.md) |
| Pricing or trial access | [Pricing test](decision-checks/pricing-test.md) |
| Public product facts for people or software | [Machine-readable product](decision-checks/machine-readable-product.md) |

A request can require several checks, but do not load a domain merely because its name appears in the conversation. In the recommendation, connect the selected check to a concrete observation, uncertainty, or scope change. Do not cite a procedure as evidence that a business claim is true.
