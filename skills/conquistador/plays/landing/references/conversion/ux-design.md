# Interaction and readability review

Specify behavior the implementation can actually be checked against. Mark planned behavior as
planned until the selected target has been built and tested. Do not infer a framework from a nested
unrelated application or manufacture an implementation stack for a bounded copy request.

## Reading and navigation

Describe heading order, section order, link purpose, and the primary task. On narrow screens, keep
related conditions with their actions and preserve source order. Avoid relying on hover, color,
animation, or an image alone to carry essential meaning. Declare what an absent asset should show.

## Actions and forms

For each action record destination, commitment, idle/pending/success/failure state, repeated-click
behavior, and recovery. For each form field record purpose, optionality, validation, error text,
and data handling assumptions. A proposed success message must match the actual backend result.

## Accessibility checks

Specify keyboard access, visible focus, labels, error association, readable contrast, meaningful
alternative text, and reduced-motion behavior where applicable. Verify these in the implementation;
a checked box in a prose brief is not evidence of conformance. Use the target's actual viewports and
input methods for testing, and report untested combinations.

## Avoid accidental pressure

Do not hide refusal, cancellation, price, or material conditions. Keep permission separate from
unrelated actions. An animation or repeated call to action should serve comprehension or navigation,
not obstruct leaving. Prefer a simpler interaction when the proposed detail has no task benefit.
