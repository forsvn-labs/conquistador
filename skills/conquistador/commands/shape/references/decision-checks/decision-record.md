# Define the decision

Use this check when the request leaves several plausible actions open. Start with the decision the user can make now. Separate that decision from the result they hope it will cause.

## Establish the boundary

Write a sentence naming the affected user, the change in their work, and the constraint that matters. Record who can approve the action. If an action affects another team, budget, or customer commitment, identify that authority before treating it as available.

List the current behavior and the proposed behavior side by side. An implementation request may already settle this question; do not reopen it without a concrete conflict.

## Compare feasible choices

Include the current approach when it remains feasible. Compare alternatives against the same outcome and constraints. Estimate effort and failure cost separately. A cheap experiment can still create an expensive promise.

For each option, record:

- What must be true for it to work, and what evidence supports that condition.
- What it commits now and what it leaves open.
- How someone would detect failure before increasing the commitment.
- What can be restored, by whom, and at what cost.

Recommend an option with the evidence that distinguishes it. If the evidence cannot distinguish options, propose the smallest useful observation that can. Do not manufacture numerical rankings from preferences.

## Decision record

Return the choice, reason, unresolved condition, next action, owner, and review trigger. Mark each supporting statement as observed, reported, estimated, or unknown. Retain rejected alternatives only when the reason prevents a likely future mistake.

## Example, synthetic

A team wants automatic reminder emails. The current problem is missed handoffs, but the cause is unknown. Compare a visible owner field, an internal reminder, and customer email. Check handoff records before recommending customer contact. The approved next step may be a local record review; it does not authorize sending messages.

## Limit

This check organizes a decision. It does not establish customer demand or grant spending authority. Use the demand and commitment checks when those are unresolved.
