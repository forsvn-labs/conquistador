# Use evidence from prior attempts

Use when the user cites a previous launch, project, or failed approach as a reason to proceed or stop.

## Recover what happened

Record the original objective, actions taken, result, and available records. Separate a measured outcome from the explanation people gave it afterward. Preserve missing data instead of filling it with a familiar success or failure story.

Compare the present situation with the prior attempt: user need, team capacity, distribution, technology, cost, and constraints. Only differences that affect the causal explanation should change the recommendation.

## Test the lesson

For each claimed lesson, state the observation that supports it and an alternative explanation. Ask whether the proposed decision would still make sense if the favored explanation were wrong. If not, test that assumption before making a larger commitment.

Exclude sunk effort from the case for future spending. Include reusable assets only when their current condition and use rights are known. Experience can reduce an estimate's uncertainty; it does not prove demand.

## Output

Return a table of prior observation, proposed lesson, current applicability, and next verification. Preserve the source of each historical claim. End with the decision that the available evidence supports now.

## Example, synthetic

A previous launch had little adoption during an outage. That result cannot by itself show that the audience rejected the offer. Verify availability and reach before changing the product premise. A later trial must still justify its own cost.

## Limit

Retrospective accounts can omit failed experiments and contextual factors. State uncertainty when records are unavailable. Never substitute another founder's story for this project's evidence.
