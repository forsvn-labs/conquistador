# Plan a multi-touch sequence

Use when a request covers more than one touch. Each touch must make sense alone and add one
element that earlier touches did not contain. This file sets no schedule and predicts no reply
rate; the sender owns the cadence, and only an authorized test can measure it.

## Give each touch one new element

The first touch carries the full context: who is writing, why this reader, what is proposed, and
one ask. Each later touch adds exactly one new element and may change one of these:

- **Angle:** a different use case or consequence of the same problem, still stated conditionally.
- **Asset:** a sample output, an existing document, authorized terms that reduce the buyer's risk,
  or one verified result from a comparable customer within its documented scope.
- **Ask:** a smaller or different decision, such as a one-line reply instead of a call, or a
  close-the-loop question that is easy to answer with "not now".

Before drafting, write one row per touch: new element, its source, and the ask. If a row has no
new element, end the sequence before that touch. Do not restate the first pitch in new words,
and do not send "just following up" or "bumping this" as the whole message. Never imply that
silence creates a debt, a prior conversation, or agreement.

## Choose the spacing

Do not use fixed day counts. Set each gap from evidence the sender has, and record it as the
sender's decision:

- **Buyer's cycle:** how often the relevant work recurs for this reader, such as a month-end close
  or a release cycle. Time a touch to that cycle only when the sender knows it; do not guess.
- **Sender's capacity:** the sender must be able to answer replies and deliver every offer (a
  first run, a pilot call) within the time the copy states. Plan fewer touches if not.
- **Reply handling:** leave enough time for a reply to arrive and pause the sequence before the
  next touch goes out.

Do not write timing claims into copy that depend on the real send gap, such as "last week". Use
"I wrote earlier" or omit the reference.

## Write follow-up subjects

- **Reply in the thread** when the touch depends on the earlier message, such as a sample promised
  in it. Use the sending tool's real reply function so that the earlier message stays below. Keep
  the original subject; the tool adds any reply prefix.
- **Use a new subject** when the touch changes the angle or the ask enough to stand alone, or when
  the reader may not have seen the earlier message. The subject must describe this touch.
- Never type "Re:" or "Fwd:" on a new message. Mark the threading choice for operator review,
  because the sending tool decides how threads behave.

## Fit length to the new element

Write the new element, the least context needed to read it, and the ask. Restate affiliation in
one line when the touch has a new subject. A plain question can be very short; a sample output
needs the lines that show it. Do not trim a needed qualification to make a touch shorter.

## Stop the sequence

End the sequence when any of these happens:

- the planned touches are sent;
- no new element remains for the next touch;
- the reader replies on any channel, unsubscribes, bounces, or complains;
- the sender can no longer deliver the offer in the copy (update or stop; never turn a real
  capacity limit into pressure);
- a deliverability or compliance boundary set before sending is crossed.

Write "this is my last email" only when the sender will suppress further touches.

## Stop on a reply from any channel

A reply by email, direct message, phone, or a colleague's forward pauses every scheduled touch for
that contact before anyone classifies it. An automatic reply also pauses the sequence until a
person decides. Use the state table in [the method](../method.md) and handle the reply with
[objections](objections.md). Resume only with a new approval for the exact next message.
