# early-stage

Use when the sender has no publishable proof yet: no users, no measured results, or results
without a case study the sender may publish. Combine it with the matching sell mode, such as
[saas](saas.md) or [services](services.md). That mode bounds the claims; this file says what to
offer in place of proof so that each touch still gives the reader something to judge.

## Say where the product stands

Find the stage the sender confirmed. State that stage once, in plain words, where a reader would
otherwise assume adoption. Do not apologize for it in every touch, and do not hide it behind
"teams like yours" or "companies we work with". The stage is a fact about the sender, not a pitch.

| Stage the sender confirmed | The copy may say | The copy must not say |
|---|---|---|
| No users yet | The product is new and no one uses it yet | Any user, pilot, or result |
| Users, but no measured results | Who uses it and how, only as the sender describes it (for example, a count of pilot teams). Names only with permission | "No customers" or "no one uses it". Any outcome, or "customers" for users the sender does not call customers |
| Measured results, but no publishable case study | A result only in the words, scope, and form the sender allows to be shared, such as unnamed | "No customers" or "no results". A named customer or a broader result than the sender stated |
| Not stated, such as "no case studies" alone | "We have no published case studies yet", or nothing about the stage | Anything about users or results |

Never upgrade or downgrade the stage. "No case studies" does not mean "no customers", and "a few
pilot teams" does not mean "customers". If the copy needs a stage the sender did not state, ask
for it as a pre-send gap.

## Choose an honest substitute for proof

Use one substitute per touch. Each one needs input from the sender before it appears in copy. If
the sender cannot supply that input, do not use the substitute; ask for it as a pre-send gap.
Show the gap where that touch would go: the substitute, the missing input, and the questions for
the sender. Do not draft the touch with invented input and list the input as an assumption later.

| Substitute | Fits when | Sender supplies first | Write it as |
|---|---|---|---|
| Design-partner or pilot offer | The sender can work closely with a small number of early users and wants their feedback | What the partner gives (time, access, feedback), what they get, who does the work, how either side exits, and how shared data is handled | Both sides of the exchange and the exit. If terms are not set, say they are to be agreed. Do not invent a free period, discount, seat count, or duration |
| First run on the prospect's own data | The product can run on an export or a limited-access connection, and the sender has time to run it and explain the output | The exact access needed, who runs it, what the output is, and when the copy is deleted | Proposed work to agree on before any access. Do not imply findings before the run, and do not call it an audit that already exists |
| Sample output from public or synthetic data | The output is easier to judge by sight than by description | The real output of a real run, its data source, and permission to share it | Labelled in the copy as built from public or synthetic data. It shows the format, not a result. Never show a real company's data without permission |
| The founder's reason for building it | The founder met the problem directly in earlier work | The true account and permission to share its details | One or two sentences about the problem, not a hero story. It explains the sender's interest; it does not show that the recipient has the problem |
| A specific observed problem | The sender has a sourced observation about the problem in the segment or about this recipient | Source, date, and access class, under [selection evidence](../frameworks/personalization-signals.md) | The observation, then a conditional link to the recipient. A segment observation is not a recipient signal |

Plan which substitute each touch carries with [sequence mechanics](../frameworks/sequences.md).
A sample output or a pilot offer is usually a stronger later touch than a second description of
the product, because the reader can judge it without trusting the sender.

## What never substitutes for proof

- Invented customers, logos, quotes, or "teams like yours" phrasing that implies adoption.
- Projected savings or outcomes written as if measured, including "could save up to" estimates.
- A waitlist, sign-up count, or investor name presented as evidence that the product works.
- A testimonial from an advisor, friend, or investor who has not used the product for real work.
- The founder's credentials presented as evidence that the product works.
- A sample output described as a customer's result, or a first run described as already done.
- A "free" offer with obligations, data access, or follow-up the copy does not state.
- Scarce pilot places or a deadline that the sender has not actually set.

## Choose the next step

Ask for one decision the reader can make without proof: a one-line answer about current practice,
a yes to see the sample, or a reply to talk through pilot terms. State the access, time, and data
handling the next step needs, or mark them as unknown for sender review. A reply never authorizes
data access or enrolls the reader in a pilot.
