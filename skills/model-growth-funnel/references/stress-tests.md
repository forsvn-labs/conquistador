# Test the model's decision sensitivity

Start from the base model and its explicit assumptions. Select inputs whose uncertainty could change the recommendation. Do not choose a universal percentage reduction for every business.

## Construct scenarios

For each selected input, use an observed range or a clearly labeled user assumption. Calculate downside, base, and upside outputs while holding other inputs fixed where possible. If inputs move together, explain that dependence and calculate the combined case separately.

Record scenario, changed inputs, output, required operational volume, cost, and decision implication. Keep arithmetic visible. A scenario is not a probability estimate unless its probability has a defensible basis.

## Check capacity and timing

Compare the required work with actual acquisition, sales, onboarding, delivery, and support capacity. Include delays and pending outcomes. A model that reaches revenue only by exceeding delivery capacity is not feasible as stated.

Check whether the result remains useful under the downside case using the user's objective. The threshold of usefulness is decision-specific. Explain loss exposure, unmet obligations, and any need for another approval.

## Find the next observation

Rank uncertain inputs by how much they change the recommendation and how practical they are to measure. Propose a bounded observation for the most consequential uncertainty. Do not request every possible metric before offering a useful decision.

## Synthetic example

A constructed model requires 40 completed onboarding tasks in a period, but the team can complete only 25. Compare extending the period, reducing the target, or adding approved capacity. Increasing an assumed conversion rate does not fix the delivery limit.

Return the recommended action, reason, unresolved condition, and review trigger. No scenario authorizes spending or proves live performance.
